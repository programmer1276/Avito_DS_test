# Техническая ревизия expanded pipeline

Проверены `prepare_expanded_train.py`, `prepare_expanded_dev.py`, `semantic_expanded_features.py`, `semantic_train_retrieval.py`, `semantic_retrieval.py`, `fit_expanded_ranker.py`, `rerank_model.py`, `semantic_features.py`, `semantic_encode.py` и схема split. Свежий holdout не открывался. Численные проверки сохранены в `retrieval_experiment_expanded_audit.json`.

## 1. Кандидаты не зависят от разметки

В новом training pipeline сначала вызывается `engine.retrieve(q)`, затем объединяются:

1. Старый пул: baseline600, body coverage250, word title150, слабее ограниченная география150.
2. coverage_both top1000.
3. title-E5 geo_mult020 top500.
4. title-E5 geo_log003 top500.

Все каналы вычисляются из запроса, признаков объявлений и обученных на reference статистик. Только после формирования `pool` читается `truth`. Строка `retrieved_truth = pool[np.isin(pool, list(truth))]` берёт пересечение, поэтому отсутствующий в retrieval positive НЕ попадает в обучение принудительно.

`chosen` включает hard70, случайные до120 из rest и все **уже найденные** positives. Такой oversampling positives допустим: он меняет частоту обучения, но не состав доступного retrieval-пула. `engine.build` получает полный реальный `pool`; ранги и относительные признаки считаются по этому пулу, а затем выбираются sampled rows. Это устраняет прежнюю проблему, когда forced positive вне retrieval становился искусственной «положительной строкой с крайними рангами».

Для каждой негативной строки inclusion probability равна 1 в hard70 и `min(1,120/len(rest))` в случайной части. Положительные строки имеют вероятность 1. Поэтому вес `1/pi` негативов корректно компенсирует sampling в пределах реального пула. К weighted-модели не следует автоматически повторно применять ту же posthoc-коррекцию odds.

## 2. Какие positives не используются при обучении

Не используются цели `truth - pool`: модель reranking не может вернуть объявление, не найденное retrieval. Они не добавляются в негативы: такой строки вообще нет в sampled матрице. Если часть целей найдена, обучаются найденные positives. Если ни одной цели нет, запрос остаётся группой только с negatives.

В train сохраняется `pool_recall = |pool ∩ truth| / |truth|`. Это позволяет отдельно посчитать потолок retrieval. На dev `n_positives` равен полному числу исходных целей, поэтому пропущенные retrieval цели остаются в знаменателе итогового Recall. Их нельзя молча вычёркивать из оценивания.

Нюанс текущего `fit_expanded_ranker.py`: вес positive делится на число найденных positives (`pc` из sampled y), а не на полное число исходных целей. Это не утечка, но меняет вес запросов с частичным покрытием: оставшиеся positives такого запроса получают повышенный вес. Для более буквального соответствия macroRecall можно нормировать на `len(rank_train_queries.item_id)`; пересборка X для этого не требуется. Выбор веса проверяется только на dev.

После завершения подготовки проверена фактическая матрица: из8468 исходных positive pairs осталось8244, вне retrieval исключены224. Все цели найдены для7777 запросов; частично найдены для10;213 групп не имеют найденных positives и остаются только с negatives. Средний pool recall равен0.9728083. Значения `pool_recall` точно совпали с числом сохранённых positives, делённым на ПОЛНЫЙ исходный denominator. Для всех сохранённых positives inclusion probability равна1.

## 3. Train/dev используют один semantic query view

В обоих pipeline запрос кодируется как `query: <search_query>` без добавления фильтров: используется `semantic_queries_title.npy`. Названия item views `title` и `full` относятся к тексту **объявления**, а не к тексту запроса.

- Train использует строки query vectors `0:8000`.
- Dev использует `8000:9000`.
- Для обеих item views применяются именно эти plain-query vectors.
- Формула geography-aware cosine везде одинакова: `max(cosine−0.6,0) × (0.2+0.8×geo) × category_factor`, где category factor равен 1 или 0.3.

Full-item представление в данном решении — заголовок, первые200 символов параметров и первые500 символов описания, дополнительно ограниченные максимальным числом токенов encoder. Это не весь неограниченный текст объявления; так и следует описывать артефакт пользователю.

Проверка файлов `.ids.csv` подтвердила порядок первых9000 запросов и соответствие первых344825 item vectors порядку train-корпуса для title и full. Это особенно важно: dev full-cosine helper соединяет векторы по позициям, а не по строковым ID.

## 4. Совпадение признаков проверено численно

На dev queries с индексами 0,1,57,333,777,999 независимо пересобраны кандидаты, все58 базовых признаков и четыре semantic-признака.

Для каждого из шести запросов:

- candidate IDs полностью совпали с `expanded_dev_features.npz`;
- y и полный denominator совпали;
- старый pool mask совпал;
- все62 признака совпали побитово с `expanded_dev_features.X + expanded_dev_full_extra.npy`;
- максимальная абсолютная разница равна0.

Дополнительно проверены train queries0,1,57,333,777,4000,7999: каждый sampled item входит в исходный реальный pool; все найденные positives включены; y и inclusion probabilities совпали; все62 признака совпали побитово с сохранённой training matrix. Таким образом, отсутствие outside-forcing подтверждено не только чтением кода, но и семью распределёнными примерами готовых данных.

При проверке использовался сохранённый feature engine; refit или изменение статистик не выполнялось.

## 5. Проверка утечки

Нормализованные тексты reference, rank_train и dev попарно не пересекаются. Количество deduplicated reference rows совпало с `engine.intent.fit_rows_`. Следовательно, проверенный intent model не обучен на rank_train/dev target interactions.

Географические и популярностные статистики для локальной проверки также строятся на reference. Текстовый индекс использует все известные документы, включая документы, являющиеся целями отложенных запросов. Это допустимо для поиска по заранее доступному корпусу; query-item связи held-out частей в эти статистики не попадают.

Item IDs используются для соединения данных и возврата ответа, но не являются признаками HGB. Query IDs и ручные правила под конкретные формулировки отсутствуют. Предобученные E5 embeddings вычисляются локально без дообучения по dev labels.

Свежий holdout исключается в коде split. Его фактическое содержимое здесь намеренно не читалось. Повторные dev-эксперименты всё равно могут переобучать выбор гиперпараметров на dev; нужна одна итоговая проверка зафиксированного решения на свежем holdout.

## 6. Что не стоит переносить в итоговый pipeline

Fallback, обученный на старом пуле с принудительными outside positives, дал хороший old-pool weighted raw Recall, но на expanded pool провалился. Это подтверждённая причина не использовать такой scorer для новых источников кандидатов. Простое увеличение пула не гарантирует улучшения: распределение feature ranks меняется, scorer должен быть обучен на согласованном пуле.

Дополнительный `fullpool_dev_features.npz` — намеренный dev-эксперимент с новым pool, а не уже проверенный final pipeline. Он добавляет два full-item semantic top300 источника. Выбирать его следует только по измеренному результату и затем сохранять ту же схему при финальной проверке и inference.

Технический момент производительности: доступ `npz[key][j]` внутри query-loop повторно читает массив NPZ. Лучше один раз загрузить нужные массивы в словарь перед циклом. Это не меняет алгоритм и разметку.

## 7. Независимый форматный валидатор

`retrieval_experiment_submission_validator.py` не импортирует retrieval/ranker. Он проверяет UTF-8 CSV, точный заголовок, все query IDs с сохранением регистра, отсутствие повторов/пропусков/лишних строк, формат и принадлежность item IDs, пробелы и число кандидатов. Флаг `--require-50` дополнительно требует ровно50 кандидатов. Проверки используют явные ошибки, поэтому не отключаются запуском Python с `-O`.

Форматная проверка не является оценкой Recall. Для привязки проверки к точному файлу отчёт содержит SHA-256 CSV. Путь к финальному CSV пока не задан; валидатор готов и проверен на небольших положительных и отрицательных примерах, но финальный answer ещё не объявляется проверенным.
