# Avito DS — поиск 50 объявлений для запроса об услугах

В этом решении я собираю кандидатов для поисковых запросов об услугах. На входе — текст запроса, его локация, категория и фильтры. На выходе — 50 идентификаторов объявлений из заданного корпуса.

**Результат отправленного файла: Recall@50 = 0.882835.** На платформе это отображается как **0.88 балла из 1**. В корне проекта лежит именно этот `answer.csv`.

Основная идея: сначала собрать достаточно широкий набор объявлений несколькими способами поиска, затем выбрать из него 50 с помощью модели на числовых признаках. По словам удобно находить точные совпадения, эмбеддинги помогают с разными формулировками, а география и свойства объявления уточняют выбор.

## 1. Как я понимаю задачу

Это этап кандидатогенерации. Среди большого корпуса нужно оставить небольшой набор объявлений, который затем сможет обработать следующий этап поиска.

Например, по запросу «монтаж видеодомофона» нужно найти объявления исполнителей, которые оказывают такую услугу. В заголовке при этом может быть «Установка домофонов» или более общее «Монтаж систем безопасности». Поэтому одного точного совпадения текста недостаточно.

Для этой задачи важна полнота: если нужное объявление не вошло в 50 кандидатов, дальнейшее ранжирование его уже не вернёт. При этом внутри этих 50 могут оставаться лишние объявления — непосредственно метрика их не штрафует. Но каждое такое объявление занимает место, которое могло достаться положительному.

### Как считается Recall@50

Для одного запроса:

```text
Recall@50 = число найденных положительных объявлений / число всех известных положительных объявлений
```

Затем берётся среднее по запросам. Например, если у трёх запросов значения равны `1`, `0.5` и `0`, итог будет `(1 + 0.5 + 0) / 3 = 0.5`.

Это среднее по запросам, а не доля найденных положительных пар во всей таблице. Запрос с большим количеством положительных объявлений не получает дополнительный вес. Порядок объявлений внутри top-50 на метрику не влияет.

## 3. Общая схема решения

```text
Текст, локация, категория и фильтры запроса
                    |
      Лексические источники + E5 по заголовкам
                    |
     Объединение кандидатов и удаление повторов
                    |
          62 признака для каждой пары
                    |
          HistGradientBoostingClassifier
                    |
             50 разных item_id
```

На dev средний объединённый набор содержит около **1 475 объявлений**. Дальше в описании я называю его пулом кандидатов.

Бустинг здесь служит внутренним способом сократить большой пул до 50. Конечный продукт решения всё равно соответствует заданию: это набор кандидатов для следующего этапа, а не ранжирование всего корпуса.

## 4. Поиск по тексту

### Нормализация

Для лексических методов текст приводится к нижнему регистру, `ё` заменяется на `е`, обрабатываются HTML-сущности, удаляются лишняя пунктуация и пробелы. Для русских слов используется Snowball-стемминг — приведение к основе слова.

Это помогает сопоставлять словоформы. При этом стемминг не решает задачу синонимов и не заменяет понимание смысла. Вручную исправленных запросов или отдельных словарей ответов под benchmark нет.

### BM25 по заголовку и описанию

Заголовки короткие, а описания часто длинные и содержат перечни услуг. Поэтому для них используются два отдельных индекса. BM25 учитывает редкость слова и длину документа: совпадение редкого слова обычно полезнее совпадения общего.

Параметры в текущем коде:

| Индекс | Текст | Параметры |
|---|---|---|
| Заголовок | Заголовок после стемминга | `k1=1.2`, `b=0.3` |
| Описание | Первые 3 500 символов описания и первые 1 500 символов параметров | `k1=1.2`, `b=0.65` |

Итоговая BM25-оценка делится на сумму IDF известных слов запроса. Поэтому признак в коде — нормированная поисковая оценка, а не вероятность релевантности.

### TF-IDF и покрытие слов

Используются ещё два текстовых представления:

- **Символьный TF-IDF по 3–5-граммам заголовка.** Помогает находить похожие написания и часть опечаток.
- **Словарный TF-IDF по словам и биграммам заголовка после стемминга.** Дополняет BM25 сочетаниями слов.

Отдельно считается доля разных слов запроса, которые встретились в заголовке или описании. Есть обычная и взвешенная по IDF версии. Если слово запроса неизвестно индексу, оно остаётся в знаменателе: совпадение одного известного слова из двух не должно считаться полным покрытием запроса.

### Основная лексическая оценка

Обозначения `title`, `body`, `char` и `filters` — оценки соответствующих индексов. Базовая смесь выглядит так:

```text
lexical = 0.50 * title + 0.35 * body + 0.15 * char + 0.10 * filters
baseline = lexical * (0.20 + 0.80 * geo) * (0.30 + 0.70 * category_match)
```

Здесь `category_match = 1`, если категории совпадают или категория поиска равна нулю, то есть не задана.

Текстовые фильтры используются как дополнительный поисковый сигнал. Например, условие про рейтинг не превращается в строгую проверку `rating >= 4`. Это ограничение текущей реализации: параметры помогают отбору, но полное логическое выполнение всех фильтров не гарантируется.

## 5. Почему география учитывается мягко

Поисковая локация и локация выбранного объявления не всегда совпадают. Пользователь может искать по области, а исполнитель указал конкретный город. Для удалённых услуг расстояние вообще может быть менее важным.

Поэтому объявления из другой локации не отбрасываются сразу. Географический сигнал строится из трёх частей:

1. При точном совпадении `location_id` значение равно 1.
2. Если можно оценить центр поисковой локации, используется близость `0.8 * exp(-distance_km / 40)`.
3. По обучающей истории оценивается совместимость пары «локация поиска — локация объявления».

Из мягких сигналов берётся максимум, а точное совпадение устанавливает 1. Историческая оценка нормируется на максимальную частоту для данной поисковой локации с добавкой 5 в знаменателе. Это мера совместимости, а не распределение вероятностей с суммой 1.

Центры локаций — медианные координаты объявлений текущего корпуса. Точных координат пользователя в данных нет. Если центр определить нельзя, остаются другие географические сигналы и текстовый поиск.

Даже низкий `geo` не обнуляет базовую оценку благодаря нижней границе 0.2. Отдельный источник с более слабым штрафом за географию дополнительно сохраняет часть дальних кандидатов.

## 6. Смысловой поиск с E5

Для смыслового сходства используется открытая модель **`intfloat/multilingual-e5-small`**. Я не дообучаю её на этом задании: она переводит тексты в векторы, которые дальше сравниваются между собой.

Подготовка входов:

| Представление | Текст | Максимальная длина |
|---|---|---:|
| Запрос | `query: ` + исходный текст запроса | 64 токена |
| Объявление: заголовок | `passage: ` + заголовок | 64 токена |
| Объявление: расширенный текст | Заголовок, первые 200 символов параметров, первые 500 символов описания; префикс `passage: ` | 128 токенов |

Фильтры не добавляются к E5-вектору запроса. Они используются в других частях решения. Векторы имеют размерность 384 и нормируются по L2, поэтому скалярное произведение соответствует cosine similarity.

**В итоговой конфигурации E5 по заголовкам участвует в извлечении кандидатов.** Расширенный текст добавляет признаки для бустинга, но не является отдельным источником кандидатов этой версии.

Для E5 по заголовкам используются два варианта поправки на географию: умножение на мягкий географический коэффициент и более плавная добавка через логарифм. Они находят частично разные объявления. Точные формулы находятся в `candidate_pool()` в [solution_pipeline.py](solution_pipeline.py).

Обрезка описаний сокращает затраты на расчёт. Обратная сторона — услуга, упомянутая только в конце длинного текста, может потеряться.

## 7. Как собирается пул кандидатов

| Источник | Максимум кандидатов до объединения |
|---|---:|
| Основная лексическая смесь | 600 |
| Та же смесь с учётом покрытия слов в описании | 250 |
| Словарный TF-IDF заголовка с географией и категорией | 150 |
| Лексическая смесь с более слабым географическим штрафом | 150 |
| Смесь с покрытием слов в заголовке и описании | 1 000 |
| E5 по заголовку, мультипликативная поправка | 500 |
| E5 по заголовку, логарифмическая поправка | 500 |

После объединения повторяющиеся объявления удаляются, поэтому размер пула меньше суммы квот. Смысл нескольких источников в том, чтобы не зависеть от одной формулы: точное совпадение, описание услуги и смысловая близость могут давать разные полезные кандидаты.

Пул строится только по признакам запроса и объявления. Известные положительные ответы из разметки не добавляются в него задним числом.

## 8. Признаки и модель отбора

Для каждой пары «запрос — кандидат» рассчитываются **62 признака**. Их порядок зафиксирован в [models/feature_names.json](models/feature_names.json) и проверяется перед предсказанием.

| Группа | Количество | Примеры |
|---|---:|---|
| Текстовое соответствие | 11 | BM25, TF-IDF, покрытие слов, вхождение запроса в заголовок |
| Оценки поисковых источников | 21 | Оценка, ранг и оценка относительно максимума для семи источников |
| География и её история | 6 | `geo`, совпадение локации, наличие центра, характеристики истории |
| Свойства объявления | 9 | Длины текстов, цена, рейтинг, отзывы, флаги способов связи |
| Запрос и категория | 6 | Длина запроса, фильтры, категория, доставка |
| Совместимость типа услуги | 5 | Признаки классификатора микрокатегорий |
| E5 | 4 | Сходство двух текстовых представлений и сочетание с географией |

Оценки источников имеют разные масштабы. Поэтому кроме самой оценки передаются ранг внутри пула и отношение к максимуму. Ранг преобразуется через `log1p`. Все эти величины считаются **по полному пулу**, до отбора строк для обучения.

### Классификатор типа услуги

Дополнительная модель `MultinomialNB` по тексту запроса и фильтрам предсказывает микрокатегорию услуги. Вход — объединение словарного и символьного TF-IDF, параметр сглаживания `alpha=0.2`.

Дубли взаимодействий убираются. Одинаковые тексты с одной микрокатегорией объединяются, их вес равен корню из числа наблюдений. Это уменьшает влияние наиболее частых сочетаний.

Для каждого кандидата бустинг получает оценку его микрокатегории, её относительное и логарифмическое значения, совпадение с самым вероятным классом и уверенность классификатора. Эти числа используются как дополнительные признаки. Они не являются калиброванной вероятностью релевантности самого объявления.

### Работа с числовыми признаками

Цена, число отзывов и некоторые длины преобразуются через `log1p`, чтобы уменьшить влияние очень больших значений. Пропущенный рейтинг остаётся `NaN`: бустинг умеет работать с пропусками. Отсутствующие тексты для индексации заменяются пустыми строками.

В схеме сохранено название `price_missing_or_negative`. В текущей реализации этот флаг проверяет именно отрицательную цену; настоящий `NaN` остаётся пропуском в `log_price`. Код и схема оставлены согласованными с обученной моделью.

### Почему выбран бустинг

`HistGradientBoostingClassifier` объединяет числовые признаки и позволяет учитывать их сочетания. Например, одинаковое текстовое сходство может означать разное при совпавшей и далёкой локации. Фиксированной линейной суммой такие зависимости описать сложнее.

Основные параметры:

| Параметр | Значение |
|---|---:|
| `max_leaf_nodes` | 31 |
| `max_iter` | 500 |
| `learning_rate` | 0.06 |
| `l2_regularization` | 10 |
| `min_samples_leaf` | 40 |
| `max_bins` | 127 |
| `random_state` | 20260929 |
| `early_stopping` | `False` |

После предсказания остаются 50 кандидатов с наибольшей оценкой положительного класса. Дополнительные поправки на baseline и sampling score в финальной конфигурации выключены. При равных оценках используется детерминированный порядок строк корпуса.

## 9. Как устроены обучение и валидация

### Разбиение по текстам запросов

Случайное разбиение строк могло бы завысить результат: один текст запроса оказался бы и в обучении, и в проверке. Поэтому группы задаются **нормализованным текстом**. Разные города или фильтры одного текста не позволяют ему перейти в другую часть выборки.

| Часть | Размер | Для чего нужна |
|---|---:|---|
| Reference | 62 206 текстов, 405 404 исходные строки | История локаций и классификатор микрокатегорий |
| Обучение бустинга | 8 000 других текстов | Пары кандидатов и метки для HGB |
| Dev | 1 000 запросов | Сравнение настроек |
| Новый holdout | 1 500 новых текстов | Проверка после фиксации модели |

Ещё до этого разбиения использовались 2 000 dev/test-текстов. Они исключены из reference и нового holdout; текущий dev из 1 000 запросов входит в эти 2 000. Поэтому строки этой таблицы не нужно суммировать как полное разбиение всех 73 706 текстов: ещё 1 000 старых проверочных текстов остаются вне перечисленных частей.

Для обучения бустинга и нового holdout выбирается один вариант контекста на текст запроса. У него сохраняются все известные положительные объявления. Разбиение и выбор контекстов воспроизводятся в [splits.py](splits.py).

Текстовые индексы локальной проверки используют признаки всех 344 825 уникальных объявлений train. Это моделирует доступный поисковый корпус. При этом взаимодействия проверочных групп исключены из статистик, классификатора микрокатегорий и обучения бустинга.

Дат событий в наборе нет, поэтому такая проверка оценивает перенос на новые тексты запросов, а не качество на будущем временном периоде.

### Откуда берутся отрицательные примеры

Для каждого обучающего запроса сначала строится обычный пул. Из него берутся:

- 70 лучших кандидатов основной лексической смеси;
- 120 случайных кандидатов из оставшейся части, либо все оставшиеся, если их меньше;
- все известные положительные объявления, которые **уже находятся в пуле**.

Повторы удаляются. Такой отбор оставляет и сложные примеры, и более разнообразную случайную часть, не заставляя обучаться на всём корпусе.

Из **8 468** известных положительных пар обучающих запросов в пуле находятся **8 244**. Остальные **224** не подмешиваются. Получается **1 521 023 обучающих строки**.

### Веса примеров

Случайный отрицательный пример получает вес `1/p`, где `p` — вероятность его включения. Для обязательных отрицательных примеров вес равен 1. Это компенсирует то, что случайная часть представляет больший набор оставшихся кандидатов.

У положительных примеров одного запроса суммарный вес равен 50: каждый получает `50 / число найденных положительных объявлений этого запроса`.

Это практическая взвешенная классификация, а не точная оптимизация Recall@50. Выход модели используется для относительного сравнения кандидатов; трактовать его как вероятность пользовательского выбора не стоит.

## 10. Результаты проверки качества

| Выборка | Запросов | Лексический baseline | Итоговая модель |
|---|---:|---:|---:|
| Dev, выбор настроек | 1 000 | 0.835083 | 0.914333 |
| Новый holdout после фиксации модели | 1 500 | 0.799667 | 0.894556 |
| Платформа, отправленный CSV | 2 452 | — | **0.882835** |

На отложенной выборке улучшение к baseline составляет **0.094889**, или примерно **9.49 процентного пункта**.

Dev использовался при сравнении настроек, поэтому его оценка может быть оптимистичной. Новый holdout был проверен после фиксации конфигурации, без подбора параметров по его ответам.

На holdout выполнен bootstrap по запросам: 3 000 повторов, seed `20260929`.

| Величина | 95% bootstrap-интервал |
|---|---|
| Recall итоговой модели | `[0.878889; 0.909003]` |
| Парный прирост к baseline | `[0.079219; 0.110444]` |

Для прироста в каждом повторе сравниваются результаты на одних и тех же запросах. Эти интервалы описывают локальное измерение. Они не задают ожидаемый диапазон скрытого результата платформы, потому что там другие запросы и другой корпус.

При окончательном предсказании индекс строится по `benchmark_items`, история и классификатор микрокатегорий — по полному доступному train. Бустинг остаётся выбранной моделью. Это отличается от локальной проверки, где обучающие взаимодействия ограничены reference-частью.

Подробные числа сохранены в [results/fresh_holdout_metrics.json](results/fresh_holdout_metrics.json), результат платформы — в [results/platform_result.json](results/platform_result.json).

## 11. Какие ошибки я разбирал

На dev у итоговой модели найдено **966 из 1 056** положительных объявлений. Это количество найденных пар; Recall по запросам считается отдельно и равен `0.914333`.

| Причина потери | Положительных объявлений | Потеря macro Recall |
|---|---:|---:|
| Нужное объявление не попало в пул | 26 | 0.023667 |
| Попало в пул, но оказалось ниже top-50 | 64 | 0.062000 |

Потолок текущего пула на dev — **0.976333**. Большая часть оставшейся потери возникает при сокращении пула до 50. Поэтому просто добавить ещё один источник поиска недостаточно: нужно также лучше выбирать среди уже найденных вариантов.

В анализе выделились следующие ситуации:

| Ситуация | Что помогает в текущем решении | Что остаётся сложным |
|---|---|---|
| Узкая услуга указана внутри общего объявления | Поиск по описанию, покрытие слов, E5 | Несколько похожих общих объявлений трудно различить |
| Поиск по области, услуга в другом городе или удалённо | Мягкая география и источник с меньшим штрафом | Географический штраф всё ещё может быть слишком сильным |
| Опечатки и разные написания | Символьный TF-IDF, стемминг, E5 | Редкие названия и транслитерация |
| Услуга упомянута далеко в описании | Частичное использование описаний | Обрезка текста может убрать важное упоминание |
| Похожих объявлений много, но выбран только один исполнитель | Рейтинг, отзывы и другие свойства | Нет полной разметки релевантности и всех факторов выбора |

Агрегаты находятся в [results/dev_error_summary.json](results/dev_error_summary.json). Ручных замен ответов для конкретных запросов нет. Более длинные представления описаний и отдельная обработка удалённых услуг — возможные следующие шаги, но они не входят в эту модель и улучшение от них здесь не заявляется.

## 12. Что находится в answer.csv

В файле две колонки:

| Колонка | Содержание |
|---|---|
| `query_id` | Исходный идентификатор запроса, с сохранением регистра |
| `answer` | 50 идентификаторов объявлений через один пробел |

Всего **2 452 строки**, по одной на запрос, и **122 600 кандидатов**. Внутри одного ответа ID не повторяются; все они есть в `benchmark_items.parquet`. Заголовков объявлений в CSV нет, потому что проверяющей системе нужны именно идентификаторы.

Файл сохранён в UTF-8, разделитель колонок — запятая, дополнительной колонки индекса нет. Идентификаторы обрабатываются как строки, поэтому ведущие нули сохраняются. Для просмотра лучше использовать текстовый редактор или pandas с явным строковым типом, а не пересохранять файл через Excel.

SHA-256 отправленного файла:

```text
ef4ba4b73e9cbb7821d4b7c2a1899b97f8c962adde06a81a70f81dd51c9910ea
```

Проверка формата подтверждает корректность файла, но сама по себе не измеряет Recall. Для метрики нужна разметка; для benchmark она известна платформе.

## Как воспроизвести результат

### 1. Подготовить окружение

Команды выполняются из папки `Avito_DS_test`. Использовался Python 3.12.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-notebook.txt
```

В Windows вместо `source` используется `.venv\Scripts\activate`. Для запуска только скриптов достаточно `requirements.txt`; файл `requirements-notebook.txt` добавляет зависимости для ноутбука.

Версии закреплены, в том числе для scikit-learn, PyTorch и Transformers. Для контрольного запуска их лучше не менять: сериализация модели и численные расчёты зависят от окружения.

### 2. Положить данные в data

Распакуйте исходный архив задания так, чтобы получилась структура:

```text
data/
    train.parquet
    benchmark_items.parquet
    benchmark_queries.parquet
```

Исходные таблицы не включены в репозиторий. Если они лежат в другом месте, во всех командах можно передать свой `--data-dir`.

### 3. Подготовить локальные веса E5

В полном архиве решения веса уже лежат в `models/e5-small`. Достаточно проверки:

```bash
python setup_assets.py --verify-only
```

В архиве для GitHub больших весов нет. После клонирования или распаковки такого архива выполните:

```bash
python setup_assets.py
```

Скрипт скачивает зафиксированную версию E5 и сверяет размеры и SHA-256 файлов. Загрузка нужна только для подготовки. При предсказании используются локальные файлы, `local_files_only=True` и офлайн-режим; обращения к API модели нет.

Если сеть недоступна, можно скопировать подготовленные веса из полного архива:

```bash
python setup_assets.py --source /path/to/local/e5-small
```

### 4. Проверить приложенный ответ

Это быстрая проверка без построения индексов и вычисления эмбеддингов:

```bash
python validate_submission.py --answer answer.csv --data-dir data --require-50
```

Проверяются колонки, кодировка, весь набор запросов, формат ID, количество кандидатов, повторы и принадлежность корпусу.

### 5. Выполнить ноутбук

Откройте `solution.ipynb` в Jupyter или VS Code и выполните **Run All**. При необходимости браузерный интерфейс можно установить отдельно командой `python -m pip install jupyterlab`, затем запустить `jupyter lab`.

В первой кодовой ячейке задаются `DATA_DIR` и `RUN_REPRODUCE`. Путь к данным также можно передать через `AVITO_DATA_DIR`.

По умолчанию `RUN_REPRODUCE = False`: выполняются анализ данных и проверки, а сохранённые метрики читаются из отчётов. Это не запускает повторное обучение или полный пересчёт предсказаний. В приложенном ноутбуке **все 15 кодовых ячеек выполнены без ошибок**; выводы сохранены.

### 6. Рассчитать ответ заново

Для полного расчёта используйте готовый `models/ranker.pkl`:

```bash
python reproduce.py --data-dir data --device cpu --cache-dir cache/control_cpu
```

При первом контрольном запуске каталог `cache/control_cpu` должен быть новым. Результат появится в `results/reproduced/answer.csv`, отчёт проверки — в `results/reproduced/reproduction_report.json`.

Скрипт проверяет веса E5, строит индексы, рассчитывает эмбеддинги и признаки, применяет бустинг и записывает ответ. Приложенный CSV не читается для генерации кандидатов. После расчёта результат отдельно сравнивается с ожидаемой контрольной суммой. Если формат или SHA-256 не совпадают, `reproduce.py` завершится ошибкой.

Первый запуск долгий из-за кодирования корпуса. Для работы ориентировочно нужны от 16 ГБ RAM и несколько гигабайт свободного места; это рекомендация, а не измеренный верхний предел. CPU поддерживается, GPU не обязателен. Поддержаны и параметры `--device mps` / `--device cuda` при подходящем окружении, но численные отличия между устройствами возможны.

Повторные запуски используют кэш. Если менялись код, веса или устройство, выберите новую папку `--cache-dir`: устройство не входит в текущий ключ кэша. При несовпадении SHA сначала нужно проверить окружение, данные и кэш, а не заменять рассчитанный CSV приложенным файлом.

### Что проверено в этом комплекте

| Проверка | Статус |
|---|---|
| Формат, ID и SHA-256 приложенного CSV | Пройдена |
| Состав и контрольные суммы моделей | Проверены |
| Согласованность 62 признаков с моделью | Проверена |
| Выполнение 15 кодовых ячеек ноутбука | Без ошибок |
| Повторный fit бустинга на сохранённой матрице признаков | Получены те же dev-предсказания |

| Полное повторное обучение с новым расчётом всех E5-признаков | Отдельно не проверено |

Таким образом, готовый файл и локальные метрики проверены, а незавершённый контрольный прогон не выдаётся за успешное воспроизведение всей цепочки. Статус сохранён в [results/reproduction_status.json](results/reproduction_status.json), проверка повторного fit — в [results/retraining_check.json](results/retraining_check.json).

## Повторное обучение и локальная оценка

Для получения приложенного ответа заново обучать бустинг не требуется. Но весь код обучения сохранён, чтобы можно было проверить процесс целиком.

Сначала подготовьте E5, затем сделайте копию каталога моделей, чтобы не перезаписать поставленный бустинг:

```bash
cp -R models models_retrained
python train_model.py --data-dir data --model-dir models_retrained --cache-dir cache/train --device cpu
python reproduce.py --data-dir data --model-dir models_retrained --cache-dir cache/retrained_predict --output-dir results/retrained --device cpu
```

Параметры читаются из `models_retrained/selected_config.json`. Скрипт восстанавливает разбиение, строит поисковые признаки, выбирает обучающие пары и обучает одну заданную конфигурацию. Он не подбирает гиперпараметры и не использует holdout для обучения.

Повторный fit на уже сохранённых признаках дал те же предсказания. Это не означает, что полное обучение с новыми эмбеддингами на другом устройстве даст побайтно такой же pickle: небольшие численные изменения могут повлиять на разбиения деревьев.

Повторить процедуру оценки на заранее выделенном holdout:

```bash
python evaluate_model.py --data-dir data --model-dir models --cache-dir cache/train --output-dir results/holdout_reproduced --device cpu
```

Скрипт сохраняет метрики, результаты по запросам и bootstrap-интервалы. Это воспроизведение существующей процедуры проверки, а не новая независимая выборка для дальнейшего подбора параметров.
